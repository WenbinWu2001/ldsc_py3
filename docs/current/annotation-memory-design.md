# Annotation and workflow memory design

Last updated on: 2026-09-15

This document describes the implemented memory architecture for contributors. The intended workload is testing many pathways at once: for example, 1,000 pathways in one run, with each pathway tested separately against the same baseline categories. The core design removes avoidable whole-genome annotation retention and repeated model preparation. The September 14 [confirmed decisions](annotation-memory-decisions.md#confirmed-batch-integration-2026-09-14) replace the earlier all-query LD-output accumulator with sequential query execution and output batches. The earlier [completion review](../audits/annotation-memory/completion-review.md) remains historical evidence; its broader diagnostic-retention findings are outside this narrower change.

## Ownership and lifetime

[`AnnotationBundle`](../../src/ldsc/_annotation_bundle.py) represents one complete dataset through shared metadata and chromosome descriptors. It has ordered baseline/query names, source provenance, configuration, scope, and paths needed for access. File-backed shard dictionaries contain descriptors. The explicit small-input `AnnotationBundle.from_frames(metadata, baseline_annotations, query_annotations, config_snapshot=...)` route instead owns packed binary arrays, dense float32 continuous arrays, and complete diagnostics in memory, with no staging directory. `bundle.read(chrom, rows=..., columns=...)` returns detached float32 values owned by the caller; `metadata_for_chromosome(chrom)` reads that chromosome's metadata without caching it. No property implicitly concatenates every chromosome.

[`AnnotationWorkspace`](../../src/ldsc/_annotation_storage.py) owns a unique `.ldsc-annotation-*` directory immediately below the supplied output directory. Source-backed Python preparation requires `AnnotationBuilder.run(..., output_dir=...)`. Use its returned bundle as a context manager or call `close()` after the last borrower finishes. The calculator borrows a bundle and does not close it. Closure is idempotent, deletes only owned private staging, and invalidates subsequent reads. Original inputs must remain available and unchanged while a source-backed result depends on them.

Standalone `run_annotate()` uses [`_annotation_outputs.py`](../../src/ldsc/_annotation_outputs.py) to return saved sources. It writes persistent `query.<chrom>.annot.gz` files incrementally and returns descriptors referring to those outputs and the original baseline sources. It removes its construction scratch before returning. A later explicit read can prepare output-owned private shards; the caller closes that owner when done. Persistent outputs survive closure. Direct and indexed `run_ldscore()` publish their diagnostics before releasing their private workspace, so returned diagnostic references remain valid. A single-batch `LDScoreCalculator.run(..., output_config=None)` accepts already-prepared inputs, keeps diagnostics in memory, and creates no annotation, diagnostic, temporary, logging, or result files. Multiple query batches require an output configuration; high-level `run_ldscore()` and the CLI always require an output directory.

Handled failures remove owned scratch while preserving the command's existing failure diagnostics and overwrite markers. An interrupted process can leave its private directory behind. A new run creates fresh staging and does not automatically reuse or remove abandoned directories. The existing gene-index construction transaction is the explicit exception to output-contained staging: sibling build-state, locks, staging, publication, and recovery remain governed by the [index contract](gene-ldscore-index.md).

## Bounded source preparation

[`prepare_annotation_sources()`](../../src/ldsc/_annotation_sources.py) makes two content passes over each supplied text/gzip source, in addition to header preflight. The first validates and classifies numeric columns before float32 conversion, and stages only row metadata. Discovery and preflight use contents, so selecting a chromosome never requires first loading an entire annotation matrix. Each file is scanned independently with an automatic tile targeting 16 MiB of parsed cells, estimated at eight bytes per header column, and at most 65,536 rows. After discovering the layout, metadata streams are reblocked to a common tile using the combined header width of only the files aligned together. Whole-genome column sources form one group; corresponding chromosome baseline/query shards form separate groups. Adding unrelated chromosome shards therefore does not shrink the tile. Explicit `chunk_rows` controls scanning, alignment, and the second content pass. The target sizes numeric tiles; it is not a total process RSS limit and does not include variable-length metadata strings or parser/conversion copies.

Aligned baseline/query column files are checked positionally before chromosome partitioning. Corresponding rows describe one logical SNP observation. Both identity passes read only metadata: [`DiskIdentityIndex`](../../src/ldsc/_annotation_identity.py) applies drop-all duplicate cleanup across the complete logical dataset, including cross-chromosome rsID collisions. Its SQLite table stores narrow identity/count state with an 8 MiB page cache. Parameterized lookups use at most 512 keys, reduced to the connection's variable limit when necessary; lookup dictionaries cover only the current bounded tile. Upserts commit after at most 262,144 valid rows, with the final partial transaction committed before selection. The journal stays in the workspace and any temporary IN key set is bounded by the lookup batch. Fewer statements and commits reduce execution overhead; SQL statement counts do not measure physical disk reads. Invalid allele rows are excluded from duplicate clusters under the existing rules. A chromosome shard omitting both allele columns keeps the existing base-identity fallback; an unknown allele set cannot establish a multi-allelic conflict.

After global indexing, selection writes retained metadata directly to its final Parquet file and records bounded source-row/chromosome locators in one append stream per aligned group. The retained counts size the final NumPy stores. [`_write_values()`](../../src/ldsc/_annotation_sources.py) rereads the original input at the aligned group's tile width and writes retained values directly into their final binary/continuous stores. There is no numeric `values.bin` spool, replacement numeric staging file, or conversion copy on disk. The repeated parsing/decompression is the accepted trade-off for this simpler preparation path. Inputs must remain unchanged between passes. Source metadata staging is removed after each source finishes; group selection locators are then removed. [`FrameSpool`](../../src/ldsc/_annotation_storage.py) uses one file of independently serialized frames per spool, including diagnostic spools; descriptors keep no open handles. Selection preserves source order within each chromosome and applies requested chromosome filtering only after global identity cleanup. Preparation remains serial before the gene-index builder starts chromosome workers. The [preparation benchmark report](../audits/annotation-memory/annotation-preparation.md) records the earlier dense implementation; its timing/RSS numbers are historical, not measurements of packed storage.

The subsequent [parallelism evaluation](../audits/annotation-memory/preparation-parallelism.md#decision) tested chromosome selection and writing after committing the shared global identity index. Four process workers reduced local preparation time by 25.3% on 1.89 million real baseline rows, while increasing sampled process-tree RSS from 399 to 1,075 MiB. Threads regressed, and a synthetic 1,000-query workload had no worthwhile total gain. Numeric writing did not dominate either workload. The user chose to keep preparation serial because the gains do not justify the memory and implementation costs. The parallelism follow-up is closed, including further writer-only experiments. Production preparation does not consume `--threads`; existing chromosome computation parallelism is unchanged.

## Annotation format policy

Type follows processing logic and complete value evidence, independently of baseline/query membership. No dtype flag or user-supplied type declaration is required. The [September 15 decisions](annotation-memory-decisions.md#confirmed-annotation-storage-scope-2026-09-15) govern this package-wide policy.

| Annotation source or case | Classification | Private representation |
| --- | --- | --- |
| Generated gene-list or BED membership, fixed gene control, synthetic all-ones `base` | Binary by construction, including all-zero and all-one columns | Packed bits written directly during projection/preparation |
| Supplied baseline or query annotation column containing only exact numeric 0/1 | Binary after exhaustive classification across every chunk and chromosome in the supplied dataset | Packed bits |
| Supplied column containing any other numeric value | Continuous for every chromosome of that dataset, even if individual shards contain only 0/1 or mostly zeros | Dense float32 |
| `AnnotationBundle.from_frames()` | Same exhaustive, pre-float32 classification across the input frames | Packed binary arrays and separate dense float32 arrays in RAM; no files |
| External quantile target | Separate target-value contract, not an ordinary annotation | Existing float64 storage and missing-token rules |

Classification uses parsed numeric values before float32 narrowing: for example, `1.00000001` keeps a supplied column continuous even though it rounds to one in float32. There is no sampling, tolerance, rounding-based classification, or sparse-matrix choice. Any nonbinary value in any scanned source row keeps that column continuous, including rows later excluded by identity or chromosome selection. Ordinary annotation missing/nonnumeric input errors retain their existing behavior; zero is an observed value, not a missing-value code. Existing advisory classification of fitted annotations still describes the values in its scientific analysis universe; it is separate from this source-wide storage choice.

### Encoding, identities, and order

[`ColumnStore`](../../src/ldsc/_annotation_storage.py) uses private NPY v2 files in column-major order, with separate Parquet row metadata. For a shard with \(S\) logical SNP rows, \(B\) binary columns and \(C\) continuous columns:

- The binary file has physical shape `(ceil(S / 8), B)` and dtype `uint8`. Bits run along the SNP axis within each annotation column. `bitorder="little"` puts row zero in the least significant bit; row \(r\) is bit `r % 8` of byte `r // 8`. Unused high bits of each column's final byte are zero and never become SNP rows.
- The continuous file has shape `(S, C)` and dtype `float32`. Empty type groups need no file. Supplied sources use `binary.npy` and `continuous.npy` within each chromosome directory; generated batches can add their own packed query store.
- The descriptor retains logical `n_rows`, ordered column names, logical dtype (`bool` for packed columns), NPY data offset, and explicit bit order. The NPY header describes physical shape/dtype/order. Descriptors carry this information to workers; a packed NPY file alone does not describe its logical SNP axis or names.
- All stores in one shard use exactly the same metadata row correspondence. Partial writes preserve neighboring bits at shared byte boundaries. Selected reads preserve requested rows and columns, including duplicates; padding is excluded by the logical row count.

Logical order remains baseline columns followed by queries, each in resolved input order. Gene queries keep declaration order; filtering preserves surviving queries' relative order. [`AnnotationBundle.read()`](../../src/ldsc/_annotation_bundle.py) supplies that default list. Private multi-store `AnnotationShard.read()` requires explicit ordered columns and reuses the name-to-store/position lookup to restore the requested order. There is no additional shard-level logical-order list. Physical binary/continuous grouping therefore cannot reorder default public reads, generated `.annot.gz` columns, or LD-score output columns.

### Bounded decoding and public compatibility

Column-major storage allows selected columns to be read without loading other queries. File reads seek bounded, coalesced row runs, using at most `max_read_rows` logical rows plus up to fourteen covering-byte boundary bits per decoded run. The default is 65,536 rows. They return detached arrays and retain no memory map or value cache. In-memory packed reads extract only the requested bits. Internal binary-only reads may use Boolean arrays; `AnnotationBundle.read()` always returns float32, including binary-only and empty selections. The numerical kernels retain float64 LD-score/count/overlap accumulation and the current float32 LD-score publication policy.

The returned selection itself is materialized. Callers must select an LD block and query batch to bound its size; an explicit whole-chromosome read can still be large. The package's existing computation tiles and execution batches supply those limits. This storage change leaves LD-score accumulators, aggregation copies, chromosome workers, and batch lifecycle unchanged.

These files are private, owner-scoped intermediate artifacts. Canonical annotation text remains `.annot.gz` with generated 0/1 values, and canonical LD-score Parquet files, query-batch manifests, column order, and precision remain unchanged. Reloading saved annotations uses the same automatic preparation policy. No persistent packed-artifact format, migration, resume, or new user option is introduced.

### Size and memory evidence

Private value payload size per shard is `ceil(S / 8) * B + 4 * S * C` bytes, excluding NPY headers, Parquet metadata, and identity/diagnostic scratch. The former all-float32 payload was `4 * S * (B + C)`. Binary payload approaches a 32-fold reduction; row padding and file headers matter for small shards. Binary density does not affect packed size. Continuous density does not affect dense size. File-free retained arrays use the same payload formula, excluding their Python/NumPy and metadata overhead. Parsed input frames and returned float32 tiles remain larger transient allocations.

\(S\) is the actual annotation shard row count after annotation identity cleanup and requested chromosome selection. Supplied and generated query shards use the cleaned annotation grid, which can include SNPs absent from the retained reference panel. During LD calculation, [`MappedAnnotations`](../../src/ldsc/_kernel/ldscore_projection.py) maps the retained reference contributors onto those annotation rows; it does not create another complete dense annotation matrix. LD output rows are a further regression/output subset. Consequently, the reported 1,134,471 LD-score output rows cannot be used to size the intermediate annotation artifacts.

Local measurement on September 15 prepared `resources/baseline_ld_suites/baseline_v1.2/baseline.22.annot.gz` from the workspace and compared every decoded value against an independent pandas read aligned by SNP. All values matched; all 53 columns were classified binary. No source input was modified.

| Measured chromosome-22 quantity | Value |
| --- | ---: |
| Source and retained annotation rows | 141,123 |
| Packed value payload | 934,973 bytes |
| Packed NPY file, including header | 935,101 bytes |
| Separate Parquet metadata file | 2,125,835 bytes |
| Equivalent float32 value payload, calculated from those dimensions | 29,918,076 bytes |

This measurement covers annotation preparation for one local baseline shard. It does not measure the 18,809-query Longleaf run, its intermediate row counts, or a new peak RSS. The user reported approximately 70 GB peak RSS during an unfinished run after four 1,000-query batches; its accounting scope has not been verified. Packing reduces annotation storage; it does not imply a 32-fold reduction in total job RSS. The accepted LD-score accumulator and aggregation memory are outside this change.

## BED and gene queries

[`_annotation_queries.py`](../../src/ldsc/_annotation_queries.py) and [`_gene_query_storage.py`](../../src/ldsc/_gene_query_storage.py) prepare query sources separately from baseline artifacts. BED intervals are normalized with bounded buffers. Gene identifiers resolve once against shared catalog lookup state; selected catalog indices and complete row audits are staged per source. Direct BED/gene projection prepares only the active execution batch, builds each query on each chromosome, and closes that private batch owner before advancing. Global source resolution, duplicate cleanup, coverage/support gates, and the shared baseline/control remain outside that loop. A fixed gene control, when requested by direct/indexed LD scoring, belongs to the shared baseline group.

Standalone [`annotate_workflow.py`](../../src/ldsc/annotate_workflow.py) accepts exactly one BED or gene-list route. Gene mode requires explicit nonnegative padding, uses catalog/build and coverage gates, and evaluates support on the cleaned baseline annotation grid. It skips empty or globally unsupported focal queries while retaining usable siblings, all-one queries, and zero-valued chromosome shards for queries supported elsewhere. It fails when all focal queries are skipped. Its audits use `annotation_snp_count`; reference-panel support remains unevaluated. Direct LD scoring evaluates support on retained reference rows and applies its additional regression-specific viability rules. See the [gene-list condition–outcome table](annotate-gene-list-decisions.md#validation-gates-and-conditionoutcome-table).

## Direct LD-score computation

[`PreparedChromosome`](../../src/ldsc/_kernel/ldscore.py) owns the current chromosome's reference reader, contributor metadata, physical-row mappings, LD-window state, selected annotation accessor, and drop diagnostics. `close()` clears these references and closes the reader, including on failure. PLINK physical SNP indices remain distinct from annotation order. The reference adapters in [`_kernel/ref_panel.py`](../../src/ldsc/_kernel/ref_panel.py) do not retain a metadata cache containing all chromosomes.

[`_kernel/ldscore_projection.py`](../../src/ldsc/_kernel/ldscore_projection.py) separates reference contributors from output rows. Every retained reference SNP can contribute to LD scores, counts, and overlap calculations, even when that SNP is absent from the regression/output set. The main accumulator is float64 and has `n_output_rows × (n_output_annotation_columns + 1)` entries; the extra column is the separately governed regression-weight projection. Completed direct scores use the existing float32 output conversion. Moving the output mask upstream does not restrict the reference contributor universe.

Within each active direct query batch, each PLINK correlation block is generated once. The next execution batch repeats reference preparation and traversal. Shared baseline columns and the weight mask are projected together, then query columns are read in batches for that same block. For parquet R2, bounded pair batches are scattered through float64 sparse products. Counts and overlap products are accumulated from bounded annotation tiles; the retained overlap summary consists of baseline-by-all-annotation products plus query diagonals, rather than a dense query-by-query matrix. Preserve the existing accumulation and validation tolerances when changing these kernels. Annotation sums reduce binary 0/1 and normalized float32 continuous values into float64, fixing batch/layout-dependent quantitative counts (completion-review R1). Independent `math.fsum` checks cover signed and high-offset values at the existing tolerances; overlap products and LD-score accumulation retain their established precision.

`--query-batch-size` defaults to **1000** for direct/indexed `ldscore` and batch `partitioned-h2`. A smaller positive value reduces active query workspace. It does not reduce the number of requested pathways or merge them into a joint regression model. With exactly 1,000 queries, the default permits all 1,000 in one active batch. The active output-row accumulator scales with batch width. Only compact counts, baseline-by-query overlaps, and diagnostic/source descriptors scale with the total requested query count; saved query LD values do not accumulate in memory.

## Chromosome parallelism

[`LDScoreCalculator`](../../src/ldsc/ldscore_calculator.py) uses `--threads` to choose chromosome worker **processes**: `1` is sequential, positive values request that many workers, and negative values follow the documented joblib convention. Positive requests are capped by the number of available chromosomes; negative requests derive their count from available CPUs and are then capped by chromosome count. Spawned workers set default native-library thread environment values; these are separate from the chromosome-worker count and do not guarantee runtime limits. `build-gene-ldscore-index --threads` uses a chromosome thread pool; both commands keep the same flag name and default to sequential execution.

The sequential lifecycle is `load chromosome → prepare → compute/write diagnostics → close → next chromosome`. Reference and annotation working arrays from the completed chromosome become available for reuse before the next preparation. Python/NumPy allocators may keep freed pages, so RSS need not fall immediately. A flat RSS trace alone is not evidence of retained chromosome objects; lifetime tests assert release directly.

Parallel submission keeps pending chromosome work bounded by the effective worker count. Tasks receive descriptors, not eager annotation matrices for every chromosome. Each worker owns its active chromosome state and releases it before advancing. Completed chromosome outputs are retained only for the active batch. `LDScoreCalculator.run()` yields that aggregate to `LDScoreDirectoryWriter.write_batches()`, which writes it privately and releases query values before requesting the next batch. The allowed per-batch join/concatenate/split path remains. Worker count and query batch size control different dimensions of memory; more workers can increase total process-tree memory and may be slower for small inputs.

**Public LD tables aggregate chromosomes within each query batch.** One batch uses `ldscore.query.parquet`; multiple batches use ordered `ldscore.query.batch00001.parquet` files. Root `metadata.json.query_batches` records each file, ordered query columns, and chromosome row groups. Baseline, counts, and overlap are shared once. `_ldscore_batch_output.py` stages all query files inside the output directory, publishes after successful computation, and writes metadata last. Handled failure closes the producer and removes owned staging while retaining available diagnostics. Resume from the last completed batch is a future feature, not supported now.

## Immutable gene-index access

[`LoadedGeneLDScoreIndex`](../../src/ldsc/gene_ldscore_index.py) retains catalog/settings metadata, chromosome component paths, and compact support summaries. Integrity validation loads and releases one chromosome at a time. Assembly uses `_indexed_ldscore_batches.py` and bounded chromosome workers. Each worker loads one operator, writes and releases every active query batch, then releases the operator before its next chromosome. The coordinator assembles private float64 fragments in deterministic chromosome order, one genome-wide query batch at a time. It does not reload the operator for every query batch. Canonical integrity checks remain intact. `threads`/`--threads` has the direct-mode convention: default 1, positive worker counts, -1 available cores, -2 leaves one free, zero invalid, capped at chromosome count.

The index builder uses the same bounded annotation preparation and chromosome scheduling. Shared baseline and regression-weight projection use one traversal; separate atom-batch traversals remain intentional. Stored operators and common payloads remain float64. Smaller query multiplications and separate validation/assembly passes can add overhead; performance claims require end-to-end measurements, not just a count of loaded operators.

## Batch regression and incremental result writing

[`LDScoreSource`](../../src/ldsc/ldscore_source.py), returned by `load_ldscore_from_dir()`, reads shared baseline/identity metadata and validates schemas without retaining all query values. `read_queries(columns)` selects only requested Parquet columns and does not cache them. Writing workflows return `LDScoreSource` directly; `read_queries(columns)` may span files and exceed generation width, preserves requested order, and imposes no RAM cap. `LDScoreResult` remains the materialized object for one active batch or a small prepared no-output calculation. Downstream `h2`, `rg`, and partitioned workflows consume only the columns they need.

[`PreparedRegressionInputs`](../../src/ldsc/regression_runner.py) shares trait alignment, baseline LD scores, row mappings, and count lookup across a batch. Each query batch is loaded/aligned once. Each model still fits its complete retained genome-wide SNP set; variance filtering, outlier filtering, counts, regression weights, and jackknife work remain model-specific. No chromosome-wise regression estimates are substituted for the genome-wide model.

`estimate_partitioned_h2_batch(..., output_dir=..., query_batch_size=1000)` writes each completed fit's category table, float64 coefficient delete values, and metadata privately through [`stage_partitioned_h2_fit()`](../../src/ldsc/outputs.py), then releases estimator details. After final stable summary sorting, the existing writer assigns canonical folders and publishes the complete query tree. The returned `PartitionedH2BatchResult` contains the aggregate summary, output paths, and `per_query_artifacts` referencing persistent files. It does not contain dictionaries of all detailed DataFrames. Baseline-only input remains one joint functional-category fit.

Explicit `continue_on_query_error=True` permits failed query regressions while preserving private staging until the scan finishes. Successful model artifacts publish with a compact attempted-query status ledger; strict mode remains the default and publishes diagnostics alone if any query fails. Failed exception tracebacks are logged and detached from the retained first exception so model arrays do not accumulate through traceback references. Panel coordinates retained with shared preparation allow post-filter block diagnostics even for rsID-only traits. See [query failure handling](partitioned-h2-results.md#query-failures-and-continuation).

## Exact global quantiles

[`_quantile_inputs.py`](../../src/ldsc/_quantile_inputs.py) and [`_quantile_storage.py`](../../src/ldsc/_quantile_storage.py) reconstruct the validated common SNP universe with bounded annotation/reference/target reads and narrow SQLite row locators. Reference/target duplicates remain fatal globally, including base-key uniqueness when omitted alleles must be inferred. External targets retain float64 values and raw missing-token semantics; they are separate from ordinary packed-binary/dense-float32 annotation storage.

The first annotation pass accumulates full-common sums, overlap products, stable centered mean/M2 statistics, and the permitted eligible target vector. It validates original model aggregates, sorts that vector to obtain the existing **exact global** boundaries, and releases it. The second pass reuses those boundaries for every chromosome and accumulates quantile sums/counts directly. There is no whole-genome fitted-annotation matrix or dense SNP-by-quantile indicator matrix. Boundary ties remain in the lower quantile. Full-common standard deviations include target-excluded SNPs, as required for standardized coefficients.

## Diagnostics and verification

Shared annotation preparation emits INFO milestones for input reading, global SNP identity checks and chromosome preparation, and successful completion with retained counts and elapsed time. A storage summary reports binary/continuous column counts and actual value-file bytes, including NPY headers but excluding metadata and scratch. There is no per-chunk progress output. Intentional gene-region exclusions are summarized once per source and role, combining line–gene pairs across audit chunks while retaining only one source's message. CM/MAF notices appear once per source during its classification pass. Complete row audits and existing failure footers are preserved; see [workflow logging](workflow-logging.md#annotation-preparation).

Annotation identity audits, gene row audits, and quantile alignment diagnostics have complete streamed output routes. Most result bookkeeping uses compact summaries or persistent paths. `FrameSpool`, `IdentityDropSpool`, `TsvDiagnostics`, and quantile `AlignmentDiagnostics` preserve the stage-specific record order without an all-chromosome diagnostic DataFrame. Gene audit rows are replayed in bounded chunks, but coverage failures still collect complete affected-gene lists in summary cells and error strings. Batch regression also retains the full legacy-sumstats projection drop table through fitting. These are the remaining diagnostic-retention gaps (completion-review R3); complete records should remain available on disk while subsequent work retains counts, bounded examples, and paths. Direct results include source-cleanup drops even for a chromosome whose annotation rows were all removed.

The focused contract tests are [`test_annotation_format.py`](../../tests/test_annotation_format.py), [`test_annotation_storage.py`](../../tests/test_annotation_storage.py), [`test_annotation_preparation.py`](../../tests/test_annotation_preparation.py), [`test_annotate_streaming.py`](../../tests/test_annotate_streaming.py), [`test_ldscore_streaming.py`](../../tests/test_ldscore_streaming.py), [`test_reference_preparation.py`](../../tests/test_reference_preparation.py), [`test_gene_index_streaming.py`](../../tests/test_gene_index_streaming.py), [`test_regression_streaming.py`](../../tests/test_regression_streaming.py), and [`test_quantile_streaming.py`](../../tests/test_quantile_streaming.py). They combine independent numerical/membership expectations with selected-read, allocation-shape, lifetime, publication, and failure tests. Packed-format checks include literal byte expectations, non-byte-aligned writes, padding, empty/duplicate/reordered selections, bounded decoding, worker descriptor transfer, global exact classification, and file-free preparation. On September 15, the full suite passed 1,812 tests and 132 subtests, with one skip; unittest discovery ran 1,000 tests successfully with one skip. Both `ldsc --help` and `python -m ldsc --help` passed. The [local benchmark harness](../../benchmarks/annotation_memory.py) measures simultaneous process-tree peak RSS, elapsed time, peak private logical disk bytes, and persistent output size separately. These measurements complement correctness and ownership tests; they do not replace them.

Matched local resource results, dimensions, reproduction commands, and limitations are recorded in [the benchmark report](../audits/annotation-memory/results.md). Peak memory, runtime, private disk, and persistent output size are reported separately; small inputs do not necessarily benefit in RSS or runtime.

September 14 sequential-query implementation, numerical/lifetime verification, and two local 1,000-query chromosome-22 benchmarks are recorded in [the batch verification report](../audits/annotation-memory/sequential-query-batches.md). Reducing generation width from 1,000 to 100 used 82.2% less peak private scratch and took 1.903 times as long, with essentially unchanged peak RSS. Whole-genome RAM and runtime figures remain conditional projections; the older benchmark report predates this implementation.
