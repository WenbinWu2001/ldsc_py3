# Annotation and workflow memory design

Last updated on: 2026-09-10

This document describes the implemented memory architecture for contributors. The intended workload is testing many pathways at once: for example, 1,000 pathways in one run, with each pathway tested separately against the same baseline categories. The design removes avoidable whole-genome annotation retention and repeated model preparation while preserving the scientific universes, numerical precision, validation gates, and canonical output formats. See the [specification](../specs/2026-09-10-annotation-workflow-memory-design.md) for the approved contract and the [implementation plan](../plans/2026-09-10-annotation-workflow-memory.md) for verification progress.

## Ownership and lifetime

[`AnnotationBundle`](../../src/ldsc/_annotation_bundle.py) represents one complete dataset through shared metadata and chromosome descriptors. It has ordered baseline/query names, source provenance, configuration, scope, and paths needed for access. Its shard dictionary contains descriptors, never a collection of chromosome DataFrames. `bundle.read(chrom, rows=..., columns=...)` returns detached values owned by the caller; `metadata_for_chromosome(chrom)` reads that chromosome's metadata without caching it. No property implicitly concatenates every chromosome.

[`AnnotationWorkspace`](../../src/ldsc/_annotation_storage.py) owns a unique `.ldsc-annotation-*` directory immediately below the supplied output directory. Source-backed Python preparation requires `AnnotationBuilder.run(..., output_dir=...)`. Use its returned bundle as a context manager or call `close()` after the last borrower finishes. The calculator borrows a bundle and does not close it. Closure is idempotent, deletes only owned private staging, and invalidates subsequent reads. Original inputs must remain available and unchanged while a source-backed result depends on them.

Standalone `run_annotate()` uses [`_annotation_outputs.py`](../../src/ldsc/_annotation_outputs.py) to return saved sources. It writes persistent `query.<chrom>.annot.gz` files incrementally and returns descriptors referring to those outputs and the original baseline sources. It removes its construction scratch before returning. A later explicit read can prepare output-owned private shards; the caller closes that owner when done. Persistent outputs survive closure. Direct and indexed `run_ldscore()` publish their diagnostics before releasing their private workspace, so returned diagnostic references remain valid. A low-level calculator run without output writing borrows private diagnostic artifacts from its input bundle; consume or publish those before closing the bundle.

Handled failures remove owned scratch while preserving the command's existing failure diagnostics and overwrite markers. An interrupted process can leave its private directory behind. A new run creates fresh staging and does not automatically reuse or remove abandoned directories. The existing gene-index construction transaction is the explicit exception to output-contained staging: sibling build-state, locks, staging, publication, and recovery remain governed by the [index contract](gene-ldscore-index.md).

## Bounded source preparation

[`_annotation_sources.py`](../../src/ldsc/_annotation_sources.py) scans each whole-genome text/gzip source once into bounded append spools. Discovery and preflight use contents, so selecting a chromosome never requires first loading an entire annotation matrix. The automatic parser tile targets 16 MiB of numeric cells across aligned sources and at most 65,536 rows. Current preparation also normalizes existing chromosome inputs into the same seekable representation; this intentionally spends temporary disk and I/O to make later row/column reads predictable.

Aligned baseline/query column files are checked positionally before chromosome partitioning. Corresponding rows describe one logical SNP observation. [`DiskIdentityIndex`](../../src/ldsc/_annotation_identity.py) then applies drop-all duplicate cleanup across the complete logical dataset, including cross-chromosome rsID collisions. Its SQLite table stores narrow identity/count state with an 8 MiB page cache. Invalid allele rows are excluded from duplicate clusters under the existing rules. A chromosome shard omitting both allele columns keeps the existing base-identity fallback; an unknown allele set cannot establish a multi-allelic conflict. The global duplicate rule is the deliberate correction to the old layout-dependent behavior.

Normalized annotation values are float32, stored column-major in private `.npy` files; row metadata is separate Parquet. [`ColumnStore`](../../src/ldsc/_annotation_storage.py) performs bounded explicit reads, coalesces requested row ranges, and returns ordinary arrays rather than memory maps. Column-major storage makes a small query batch inexpensive to read without loading every pathway. The private representation is an implementation detail, not a second public annotation format.

## BED and gene queries

[`_annotation_queries.py`](../../src/ldsc/_annotation_queries.py) and [`_gene_query_storage.py`](../../src/ldsc/_gene_query_storage.py) prepare query sources separately from baseline artifacts. BED intervals are normalized with bounded buffers. Gene identifiers resolve once against shared catalog lookup state; selected catalog indices and complete row audits are staged per source. Projection constructs one query on one chromosome at a time. A fixed gene control, when requested by direct/indexed LD scoring, belongs to the shared baseline group.

Standalone [`annotate_workflow.py`](../../src/ldsc/annotate_workflow.py) accepts exactly one BED or gene-list route. Gene mode requires explicit nonnegative padding, uses catalog/build and coverage gates, and evaluates support on the cleaned baseline annotation grid. It skips empty or globally unsupported focal queries while retaining usable siblings, all-one queries, and zero-valued chromosome shards for queries supported elsewhere. It fails when all focal queries are skipped. Its audits use `annotation_snp_count`; reference-panel support remains unevaluated. Direct LD scoring evaluates support on retained reference rows and applies its additional regression-specific viability rules. See the [gene-list condition–outcome table](annotate-gene-list-decisions.md#validation-gates-and-conditionoutcome-table).

## Direct LD-score computation

[`PreparedChromosome`](../../src/ldsc/_kernel/ldscore.py) owns the current chromosome's reference reader, contributor metadata, physical-row mappings, LD-window state, selected annotation accessor, and drop diagnostics. `close()` clears these references and closes the reader, including on failure. PLINK physical SNP indices remain distinct from annotation order. The reference adapters in [`_kernel/ref_panel.py`](../../src/ldsc/_kernel/ref_panel.py) do not retain a metadata cache containing all chromosomes.

[`_kernel/ldscore_projection.py`](../../src/ldsc/_kernel/ldscore_projection.py) separates reference contributors from output rows. Every retained reference SNP can contribute to LD scores, counts, and overlap calculations, even when that SNP is absent from the regression/output set. The main accumulator is float64 and has `n_output_rows × (n_output_annotation_columns + 1)` entries; the extra column is the separately governed regression-weight projection. Completed direct scores use the existing float32 output conversion. Moving the output mask upstream does not restrict the reference contributor universe.

For PLINK, each correlation block is generated once. Shared baseline columns and the weight mask are projected together, then query columns are read in batches for that same block. For parquet R2, bounded pair batches are scattered through float64 sparse products. Counts and overlap products are accumulated from bounded annotation tiles; the retained overlap summary consists of baseline-by-all-annotation products plus query diagonals, rather than a dense query-by-query matrix. Preserve the existing accumulation and validation tolerances when changing these kernels.

`--query-batch-size` defaults to **1000** for direct/indexed `ldscore` and batch `partitioned-h2`. A smaller positive value reduces active query workspace. It does not reduce the number of requested pathways or merge them into a joint regression model. With exactly 1,000 queries, the default permits all 1,000 in one active batch. Final HM3 LD-score tables and the output-row accumulator can still scale with total query count; this is an explicit allowance.

## Chromosome parallelism

[`LDScoreCalculator`](../../src/ldsc/ldscore_calculator.py) uses `--threads` to choose chromosome worker **processes**: `1` is sequential, positive values request that many workers, and negative values follow the documented joblib convention. The effective count is capped by available chromosomes and CPU availability. Despite the flag name, these are processes, not Python threads. Worker BLAS thread limits avoid multiplying chromosome workers by a second pool of numerical threads.

The sequential lifecycle is `load chromosome → prepare → compute/write diagnostics → close → next chromosome`. Reference and annotation working arrays from the completed chromosome become available for reuse before the next preparation. Python/NumPy allocators may keep freed pages, so RSS need not fall immediately. A flat RSS trace alone is not evidence of retained chromosome objects; lifetime tests assert release directly.

Parallel submission keeps pending chromosome work bounded by the effective worker count. Tasks receive descriptors, not eager annotation matrices for every chromosome. Each worker owns its active chromosome state and releases it before advancing. Completed HM3 outputs and compact summaries are intentionally retained for final aggregation. Worker count and query batch size control different dimensions of memory; more workers can increase total process-tree memory and may be slower for small inputs.

**Public HM3 LD tables remain aggregate files**: `ldscore.baseline.parquet`, optional `ldscore.query.parquet`, and `ldscore.overlap.parquet`, with `metadata.json`. They are never chromosome-sharded by `ldscore`. Standalone annotation shards and private chromosome artifacts serve different purposes from these public LD-score tables.

## Immutable gene-index access

[`LoadedGeneLDScoreIndex`](../../src/ldsc/gene_ldscore_index.py) retains catalog/settings metadata, chromosome component paths, and compact support summaries. Integrity validation loads and releases one chromosome at a time. Assembly makes another chromosome pass, holding that chromosome's sparse operator throughout all query batches before releasing it. It does not reload the operator for every query batch. Canonical integrity checks remain intact.

The index builder uses the same bounded annotation preparation and chromosome scheduling. Shared baseline and regression-weight projection use one traversal; separate atom-batch traversals remain intentional. Stored operators and common payloads remain float64. Smaller query multiplications and separate validation/assembly passes can add overhead; performance claims require end-to-end measurements, not just a count of loaded operators.

## Batch regression and incremental result writing

[`LDScoreSource`](../../src/ldsc/ldscore_source.py), returned by `load_ldscore_from_dir()`, reads shared baseline/identity metadata and validates schemas without retaining all query values. `read_queries(columns)` selects only requested Parquet columns and does not cache them. The public `LDScoreResult` remains the allowed materialized LD-output object. Downstream `h2`, `rg`, and partitioned workflows consume only the columns they need.

[`PreparedRegressionInputs`](../../src/ldsc/regression_runner.py) shares trait alignment, baseline LD scores, row mappings, and count lookup across a batch. Each query batch is loaded/aligned once. Each model still fits its complete retained genome-wide SNP set; variance filtering, outlier filtering, counts, regression weights, and jackknife work remain model-specific. No chromosome-wise regression estimates are substituted for the genome-wide model.

`estimate_partitioned_h2_batch(..., output_dir=..., query_batch_size=1000)` writes each completed fit's category table, float64 coefficient delete values, and metadata privately through [`stage_partitioned_h2_fit()`](../../src/ldsc/outputs.py), then releases estimator details. After final stable summary sorting, the existing writer assigns canonical folders and publishes the complete query tree. The returned `PartitionedH2BatchResult` contains the aggregate summary, output paths, and `per_query_artifacts` referencing persistent files. It does not contain dictionaries of all detailed DataFrames. Baseline-only input remains one joint functional-category fit.

## Exact global quantiles

[`_quantile_inputs.py`](../../src/ldsc/_quantile_inputs.py) and [`_quantile_storage.py`](../../src/ldsc/_quantile_storage.py) reconstruct the validated common SNP universe with bounded annotation/reference/target reads and narrow SQLite row locators. Reference/target duplicates remain fatal globally, including base-key uniqueness when omitted alleles must be inferred. External targets retain float64 values and raw missing-token semantics; they are separate from ordinary float32 annotation storage.

The first annotation pass accumulates full-common sums, overlap products, stable centered mean/M2 statistics, and the permitted eligible target vector. It validates original model aggregates, sorts that vector to obtain the existing **exact global** boundaries, and releases it. The second pass reuses those boundaries for every chromosome and accumulates quantile sums/counts directly. There is no whole-genome fitted-annotation matrix or dense SNP-by-quantile indicator matrix. Boundary ties remain in the lower quantile. Full-common standard deviations include target-excluded SNPs, as required for standardized coefficients.

## Diagnostics and verification

Annotation, gene, and quantile row-level diagnostics are streamed completely; result objects retain compact summaries, representative examples, or persistent paths. `FrameSpool`, `IdentityDropSpool`, `TsvDiagnostics`, and quantile `AlignmentDiagnostics` preserve the stage-specific record order without an all-chromosome diagnostic DataFrame. Gene summaries retain counts per source while audit rows are replayed in bounded chunks. Direct results include source-cleanup drops even for a chromosome whose annotation rows were all removed.

The focused contract tests are [`test_annotation_storage.py`](../../tests/test_annotation_storage.py), [`test_annotate_streaming.py`](../../tests/test_annotate_streaming.py), [`test_ldscore_streaming.py`](../../tests/test_ldscore_streaming.py), [`test_reference_preparation.py`](../../tests/test_reference_preparation.py), [`test_gene_index_streaming.py`](../../tests/test_gene_index_streaming.py), [`test_regression_streaming.py`](../../tests/test_regression_streaming.py), and [`test_quantile_streaming.py`](../../tests/test_quantile_streaming.py). They combine independent numerical/membership expectations with selected-read, allocation-shape, lifetime, publication, and failure tests. The [local benchmark harness](../../benchmarks/annotation_memory.py) measures simultaneous process-tree peak RSS, elapsed time, peak private logical disk bytes, and persistent output size separately. These measurements complement correctness and ownership tests; they do not replace them.

Matched local resource results, dimensions, reproduction commands, and limitations are recorded in [the benchmark report](../audits/annotation-memory/results.md). Peak memory, runtime, private disk, and persistent output size are reported separately; small inputs do not necessarily benefit in RSS or runtime.
